# Bug tracker

Severity levels:
- **Critical** — data loss, broken save/load, app crash
- **Major** — a workflow is broken but has a workaround
- **Minor** — wrong behavior, doesn't block use
- **Cosmetic** — visual only

## BUG-056 (082820261115)
**Status:** Fixed (v3 · v1.1.6)
**Severity:** Minor (follow-up gap in BUG-055's own fix, same symptom)
**Found in:** `loadProject()`'s tripgen branch (`src/main.js`) — `categoryMap` restore had no reset-before-restore and no migration for already-saved stale entries
**Description:** User report, immediately after BUG-055 shipped: "its still showing up with the workbook grouping." BUG-055 stopped NEW auto-seeding but didn't touch `categoryMap` entries a project had already saved from before the fix — those old heuristic values (written in by the now-removed auto-seed, back when the user's real project was open under the old code) were still sitting in the project file and got restored on every load exactly as before, indistinguishable at load time from a value the user genuinely set. Also found, same code path: no reset-before-restore on `tripgenCategoryMap` at all (the same BUG-027-class leak already guarded against for `tripgenQaqc` two lines below it) — a classification grouped in a previously loaded project stayed grouped when a different project with no entry for that same label loaded next.
**Fix:** Added the missing reset-before-restore. Added a load-time migration: any `categoryMap` entry that exactly matches one of `categoryFor()`'s own fixed heuristic outputs (`'Light Goods'`, `'Trucks'`, `'Pedestrian'`, `'Personal Vehicles+Peds+Pickup-Dropoff'`) gets stripped on load — a real user grouping classifications by hand essentially never types the source workbook's own internal bucket name verbatim, so this is safe. Checked against a small hardcoded list, synchronously, rather than awaiting the real async `categoryFor()` — `loadProject()` is not `async` and several call sites don't await it; an initial attempt at this fix mistakenly added an `await` inside the non-async function (caught before it reached a build, but flagged here since the user was rightly cautious about breaking anything mid-count) — the synchronous, no-async-race version was the safer fix regardless.
**Verified live:** built a fixture simulating a pre-v1.1.5 saved project (`auto`/`bike` both carrying the exact old heuristic string, `truck` carrying a genuine custom value) and confirmed on load: `auto`/`bike` show individually, `truck` keeps showing under its real custom label.

## BUG-055 (082820261101)
**Status:** Fixed (v3 · v1.1.5)
**Severity:** Minor (misleading numbers, not data loss — trip-rate totals were still mathematically correct, just grouped in a way the user hadn't chosen)
**Found in:** `groupTotals()` and its two direct-read siblings in `renderDayBlock()` (`src/analysis/ui/tripgenSection.js`), plus `categoryMap` auto-seeding in `renderTripGenSection()` and `renderTgCategoryMapEditor()` (`src/main.js`)
**Description:** User report: "the trip gen rate has groupings, but they dont match the groupings i made in classification." Every classification silently got a `categoryMap` entry auto-filled from `categoryFor()` — the source workbook's own fixed heuristic (Trucks/Pedestrian/Light Goods/Personal Vehicles+Peds+Pickup-Dropoff) — the first time the Analysis screen or the classifications editor rendered, regardless of whether the user had actually set anything. The trip-rate/totals-by-day-type cards and the classifications editor were reading the SAME `categoryMap`, so this wasn't two systems disagreeing — it was one auto-populated default silently overriding what the user thought was still unset. User's explicit follow-up: "use only the groups set in the app and if no groups set then by each classification."
**Fix:** Removed both auto-seed sites. `groupTotals()` and the two other direct `categoryMap[t]` reads in `renderDayBlock()` now fall back to the classification's own label `t` (not a shared `'Other'` bucket) when no explicit entry exists, so an unset classification shows on its own. The classifications editor still shows the heuristic as an input `placeholder` (a helpful suggestion), but it no longer writes into `tripgenCategoryMap` until the user actually types something and it commits on `change`.
**Verified live:** built a 3-classification fixture (`auto`/`truck`/`bike`) with only `truck` explicitly set to `"Truck Category"`; confirmed the trip-rate cards show `auto` and `bike` each on their own (not lumped into a shared bucket) while `truck` shows under the user's own label — and confirmed the editor's two unset fields render empty (with the placeholder suggestion visible) while the set one shows the real value.

**Description:** User report: "theres a back button on the bottom of the page that redirects to the home page for the traffic app," seen on the shared viewer. `_currentScreen` defaulted to `'home-screen'` (matching what normal boot shows first) before any real `showScreen()` call. `showScreen()`'s "push the outgoing screen onto `_navHistory`" check only tests whether `_currentScreen` is truthy — not whether a screen was ever actually rendered. **Verified live:** loaded a real shared viewer link fresh, confirmed `#app-back-btn`'s computed `display` is `none` (previously it showed and, per code, would have navigated to `home-screen` on click).

## BUG-051 (082820260957)
**Status:** Fixed (v3 · v1.1.0, found live-testing the new QA-input shareable link feature)
**Severity:** Major (a QA reviewer's browser gets permanently stuck with no way to retry or recover — the whole point of the QA-input link is a hands-off submit path a non-technical second counter can use unattended)
**Found in:** the `data-qaqc-begin` finish callback's `isQaInputMode` branch (`src/main.js`)
**Description:** The QA-input link's recount-finish path calls `await submitQaRecount(...)` to push the recount to Firestore, with the finish button's label switched to "submitting…" first. That `await` had no `try/catch` around it. Live-tested against a real (rules-rejecting) Firestore call, the promise rejected with `FirebaseError: permission-denied` — the button was left reading "submitting…" forever, with no error shown and no way to retry short of losing the recount and starting over. Any real-world submission failure (offline, a flaky connection, expired auth) would hit the same dead end, and a QA reviewer using this link has no console to see the underlying error.
**Fix:** Wrapped the submit call in try/catch — on failure, the button resets to "✓ finish recount" and re-enables, a visible message ("Could not submit — check your connection and try again.") appears under it, and an alert names the underlying error, so the reviewer can just click finish again once reconnected. On success, a confirmation banner ("✓ Recount submitted — thank you.") is now shown directly on the QA/QC screen itself, not via `setSaveState()` (which targets the sidebar's save indicator — invisible for the whole QA-input session since the sidebar never renders there).
**Verified live:** loaded a fixture Trip Gen project into QA-input mode (a temporary `window.__debugEnterQaInputMode` debug hook, removed before commit), began and finished a recount for real — confirmed the actual Firestore write attempt (network request, permission-denied rejection) and confirmed the button/sub-text correctly reset afterward rather than sticking on "submitting…".

## BUG-050 (082720261645)
**Status:** Fixed (v3 · v1.0.0, found by a dedicated pre-launch stress-test agent, per explicit instruction to stress-test the app before declaring it stable)
**Severity:** Critical (same shape as BUG-047/048 — real count data silently double-counted with zero error, zero visible indicator, via a plausible field-interruption workflow)
**Found in:** `startTripgenRecount()`'s finish closure (`src/main.js`) — the "exclude the superseded source day from analysis" step only ran inside that one-shot closure
**Description:** A non-destructive "↻ recount" (see BUG-047/048's follow-up entries) is meant to automatically exclude the original day it replaces from QA/QC and Analysis once the recount has real data. That exclusion was implemented entirely inside `startTripgenRecount()`'s own finish callback. If the recount is abandoned before finishing — navigating away mid-count, a very plausible field interruption — and later resumed via the generic `editTripgenDay()` "resume count →" path (the ONLY UI offered to recover an abandoned recount, on both the Setup screen's compact list and the Location Counts screen), that resume goes through `editTripgenDay()`'s OWN separate finish closure, which has no knowledge that this particular day is a recount-of-another-day. The recount's own data committed correctly, but the original day was never excluded — both ended up as independent, fully-counted, fully-included days for the same location, silently inflating that location's totals with no error and no visible indicator (the exclude/include toggle simply never appeared, since it's gated on `includeInAnalysis === false`, which was never set).
**Root cause:** the "which day does this recount supersede" relationship was tracked only as a closure variable (`sourceDay`), not as data on the day object itself — so any finish path other than the one `startTripgenRecount()` originally wired up had no way to know the relationship existed.
**Fix:** persist the relationship on the day itself — a new `supersedesDayIdx` field, set once when the recount day is created. Moved the exclude-step out of the closure and into `commitLocationCounts()`, the single gated write path every finish route (direct finish, abandon-then-resume via `editTripgenDay`, or any future path) already goes through — checked and applied on every successful commit to a day carrying that field, not just the first one.
**Verified live:** reproduced the exact failure against the pre-fix code shape (abandon a recount mid-count, resume via `editTripgenDay`, finish — confirmed the source day's `includeInAnalysis` stayed `true`, i.e. NOT excluded). Re-ran the identical sequence post-fix: confirmed the source day correctly ends up `includeInAnalysis: false` after finishing through that exact resume path, matching what a direct uninterrupted finish already did correctly. Also confirmed the field survives an even earlier point — a periodic autosave flush mid-count, before any finish click at all. `npm run build` passes.

## BUG-049 (082720261613)
**Status:** Fixed (v3 · v0.49.10, user-flagged: "I believe the primary driver on pass/fail is on individual classifications and not on the total tally")
**Severity:** Major (QA/QC gave a wrong verdict on real recount data — not a crash or data loss, but the exact kind of "confidently wrong" result a QA process exists to prevent)
**Found in:** `qaqcPeakHourScore` / the QA/QC Pass/Fail badge (`src/analysis/data/analyze.js`, `src/analysis/ui/tripgenSection.js`, `src/main.js`)
**Description:** The app's Pass/Fail badge was computed by summing every classification into one combined hour total, then comparing that single number against the volume-tiered threshold. Re-opened the actual source workbook (`QA_QC_Lindenwood_FedEx_flatlands.xlsx`, see `reference_qaqc_source` memory) and read its live formulas directly: it scores each FHWA category (Auto+bike+bus+moto / light truck / truck / Pedestrian) with four **completely independent** "Good"/"Failed" formulas (cells T10/Y10/AD10/AI10, e.g. `=IF(((IF(T8<=T9,1,0))+T7)>=3,"Good","Failed")`) — confirmed via a workbook-wide formula search that no cell anywhere combines the four into one number. The app's combined-total approach can hide a badly-off classification behind others that happen to balance it out in the sum.
**Reproduced live:** built a 2-classification hour (Autos primary 100 / recount 105, +5%, right at its own 5% threshold — passes; Trucks primary 20 / recount 10, -50%, badly fails its own 10% threshold). Combined: 120 → 115, only 4.2% off — scored a perfect 5/5 and a clean "✓ Pass," completely hiding that Trucks was wrong by half.
**Fix:** Made the existing (already-correct) per-classification computation (`perClassResults`) the primary signal everywhere instead of secondary/informational — new `perClassSummaryBadge()` rolls it into one glance-able badge ("✓ All classifications pass" / "✗ N/M classifications off", naming which), shown first on the QA/QC screen's card headers, the Analysis summary table's new "By classification" column, and the "explain this score →" detail screen. Per explicit user decision, the combined-total badge's own math was NOT changed or removed — it's kept as a secondary, clearly-labeled "informational only — the source has no such rating" metric, not deleted, since some reviewers may still want the whole-hour figure as a reference.
**Verified live:** re-ran the Autos/Trucks case above through the real dev server (real counter keystrokes, not synthetic data) — confirmed all three surfaces (QA/QC screen card, Analysis summary table, score-detail screen) now show "✗ 1/2 classification off" as the headline result, with the misleading "5/5 — Pass" combined figure still visible but clearly demoted and labeled. `npm run build` passes.
**Not a data-loss bug:** unlike BUG-047/048, no count data was ever lost or altered by this — every classification's raw counts were always saved correctly; only the derived Pass/Fail verdict shown to a reviewer was wrong. Included here because a QA process silently returning a false "Pass" on real recount data is a correctness failure worth the same documentation rigor.

## BUG-048 (082620262259)
**Status:** Fixed (v3.48.0-alpha.2, found by a follow-up investigation task on BUG-047: the user confirmed they DID click "finish" for Flatlands Ave before doing anything else, meaning BUG-047's own mechanism — a stale `tgPendingLocation` surviving from an unfinished edit — could not have been what happened to them, implying a second, still-undiscovered bug of the same shape existed)
**Severity:** Critical (real count data silently discarded with zero error, zero warning, and — see below — not caught by the shrink-detection failsafe either)
**Found in:** the same Trip Gen QA/QC recount-begin handler BUG-047 fixed (`data-qaqc-begin` click handler, `src/main.js`) — BUG-047's own fix (clearing `tgPendingLocation = null` before starting a recount) closed ONE hole but, in doing so, opened a second one it never accounted for
**Description:** A location's live count only ever reaches its entry's `day.parsed` — the thing that actually gets saved — through `scheduleAutosave()`'s debounced 2-second timer (its "keep the pending edit's entry current" step, which calls `tgCaptureLiveSnapshot()` and writes the result into `day.parsed`). Anything typed in the last (up to) 2 seconds before that timer fires lives ONLY in `tripgenCount.js`'s shared `tgData` module state, not yet in `day.parsed`. BUG-047's fix made the recount-begin handler null `tgPendingLocation` immediately — correct, since a recount is never a location edit — but it did this with no flush first. `tgBeginRecount()` (`tripgenCount.js` line 359) then unconditionally resets the shared `tgData` for its own use. If a QA/QC recount is started — on ANY location, not necessarily the one being edited — less than 2 seconds after the last keystroke in a currently-open edit session (a brand-new count in progress, or a finished location reopened via "edit counts"), whatever was just typed is silently discarded: the location is left exactly as it was BEFORE those keystrokes, with `day.inProgress` still `true` and no error of any kind.
**Reproduced live:** started a new location with 2 real keystrokes (Numpad7 ×2 — classification-1 IN ×2 at interval 0, i.e. `inbound:[2,0]`), then — 20ms later, well inside the 2-second debounce window — added a QA/QC time period and began a recount (real UI clicks/keystrokes throughout, via `data-qaqc-begin`). Before: interval 0 read `inbound:[2,0], outbound:[0,0]`, 1 of 96 intervals non-zero. After finishing the recount: ALL 96 intervals read zero (`inbound:[0,0], outbound:[0,0]` throughout) — the 2 keystrokes were gone with no trace, while the recount itself saved correctly to `tripgenQaqc`. Also confirmed the same loss when the recount was begun on a completely different location than the one with the pending edit (the trigger is "a recount starts while ANY edit session is live," not "a recount on THIS location").
**Fix:** Before nulling `tgPendingLocation` in the recount-begin handler, flush the pending edit's live snapshot into its own entry/day first — the exact same `tgCaptureLiveSnapshot()` capture `scheduleAutosave()` already performs, just run synchronously at this call site instead of waiting for the debounce timer, so no window of loss exists regardless of timing.
**Shrink-detection failsafe (v3.48.0-alpha.1) gap, found and fixed in the same pass:** `detectTripgenShrink()` only compared `parsed.intervals.length` (how many time-slots exist) between saves — exactly BUG-047's shape (a 96-interval day collapsing to a 4-interval day), but BUG-048's shape keeps all 96 interval slots and just zeroes their VALUES, which the interval-count check cannot see at all. Reproduced this gap directly: the corrupted save above passed `detectTripgenShrink()` with no warning, because `newCount === prevCount === 96`. Added a second, parallel check (`tgDayVolume()` + a second comparison in `detectTripgenShrink()`) that sums total inbound+outbound volume for the same day instead of counting intervals, with its own minimum-before-flagging threshold (`SHRINK_MIN_PREV_VOLUME = 8`, mirroring `SHRINK_MIN_PREV_INTERVALS`'s noise-avoidance rationale) and the same exemption for whichever entry/day is the live pending-edit target. The confirm-dialog message now names "counted vehicles" vs. "counted intervals" depending on which check fired.
**Verified live:** re-ran the identical 20ms-race repro after the fix — the location's `inbound:[2,0]` interval survived intact through the recount, confirmed in the saved project (not just the DOM). Also ran two broader real sessions through the actual UI (four locations across a full simulated 24-hour spread, 6 QA/QC time periods/recounts total, Analysis screen render, exit to "All Projects," and reopening the exact same project from the real home-screen projects list) — every location's full interval data and every recount survived byte-for-byte, confirmed via exact interval-by-interval comparison, not just non-zero counts. `npm run build` passes.
**Note on the pre-fix corrupted data left in the verification project:** one test location ("Location C - Race Test") was deliberately corrupted by this bug BEFORE the fix was applied (to nail down the mechanism) and was intentionally left in that state afterward, rather than "fixed" retroactively — matching BUG-047's own precedent that a going-forward fix does not rewrite data already lost. This is scratch test data only, not a real user's project.
**Follow-up (v3.49.0-alpha.1):** BUG-047 and BUG-048 were both, at root, the same shape — a write site trusting that `tripgenCount.js`'s shared live-counting state still belonged to the session `tgPendingLocation` claims is active, with no way to actually verify that. Rather than continuing to patch each new write site individually, replaced every direct `day.parsed =`/`day.editSnapshot =` assignment in `main.js` with a single gated `commitLocationCounts(entryId, dayIdx, parsed, editSnapshot, seq, source)` — see `DEVLOG.md`'s "read-only outside the counter" entry for the full design and a diagnostics write-log feature that came out of the same request.

## BUG-047
**Status:** Fixed (v3.47.0-alpha.6, user-reported: "theres a strange issue with loading the files, the flatlands ave locatoin only has 52 counts from 4:15pm to 5:15pm, counts were completed from 12am to 12pm")
**Severity:** Critical (real, already-completed field-count data silently overwritten — the full-day dataset was replaced with a single QA/QC recount's narrow one-hour window)
**Found in:** the Trip Gen QA/QC recount flow (`data-qaqc-begin` click handler, `src/main.js`), interacting with BUG-034's pending-location autosave mechanism — present since recounts were built, not a new regression
**Description:** Confirmed against two of the user's real save files (`830 Fountain Ave (3).tcproject` and an earlier `830_Fountain_Ave_2_REPAIRED.tcproject`) — both show Flatlands Ave's entire primary count reduced to exactly 4 intervals (16:15–17:15), matching a QA/QC recount's own `cfg` (`durationMin: 60`) for that same PM-peak window found in the file's `qaqc` data. The mechanism: `tgPendingLocation` (BUG-034's marker for "this location's edit session is still live, keep autosaving it") is only ever cleared by successfully *finishing* that edit — navigating away leaves it pointing at the location, by design, so an abandoned edit can be recovered on reload. But it was never cleared when starting a **QA/QC recount**, which reuses the exact same shared live-counting module state (`tgData`/`classifications`/`cfg` in `tripgenCount.js`) that a location edit uses. If a location's edit session was left unfinished and the user then started ANY recount, `scheduleAutosave()`'s "keep the pending edit's entry current" step (main.js) kept trusting the stale `tgPendingLocation` with no check that the live session was still actually that edit — it captured the recount's own narrow live data and wrote it straight into the stale location's `day.parsed`, silently replacing the real full-day dataset the moment the debounced autosave fired (every few keystrokes).
**Root cause:** `tgBeginRecount(...)`'s call site never cleared `tgPendingLocation`, so a stale reference from an earlier, unrelated, unfinished edit stayed "active" through an entirely different counting session that reused the same shared state.
**Fix:** Clear `tgPendingLocation = null` at the start of the QA/QC recount-begin handler — a recount is never a location edit, so it should never be mistaken for one by the autosave capture that exists specifically to protect in-progress edits.
**Verified live:** built a location with real counts spread across 3 widely-separated hours (00:00, 05:00, 10:00), finished it, reopened it for editing, navigated away WITHOUT finishing (reproducing the stale-`tgPendingLocation` precondition), started a QA/QC recount on the same location, entered real recount counts, and forced the debounced autosave to fire — confirmed pre-fix this exact sequence reproduces the corruption (the location's 3-interval spread collapses to just the recount's own narrow window); post-fix, ran the identical sequence and confirmed the location's original 3 intervals survive completely intact through the recount session and after finishing it, while the recount itself still saves correctly to `tripgenQaqc`. No console errors.
**Not addressed — pre-existing data, not recoverable by this fix:** this fix prevents the corruption going forward; it cannot restore Flatlands Ave's already-overwritten data in the user's existing save files, since the original full-day counts were genuinely replaced, not just hidden.
**Follow-up (v3.48.0-alpha.1):** this fix closes the specific mechanism BUG-047 used, but not the general class of bug (BUG-034/035/036/047 were four different root causes with the same "real count data silently gone, unrecoverable" outcome). Added a generic three-layer count-data failsafe — rolling local backups, an automatic shrink-detection check that would have caught this exact incident regardless of root cause, and an export reminder — see `DEVLOG.md`'s "count-data failsafe" entry.

## BUG-046
**Status:** Fixed (v3.47.0-alpha.5, user-reported: "there seems to be an issue moving beyond the count screens into qa/qc and analysis - they are loading up blank," confirmed with the user's own real save file — 3 locations, 24 hours of data, QA/QC recounts on 2 locations)
**Severity:** Major (real, already-entered QA/QC recount data became permanently unreachable in the UI, not just slow to appear — user-visible as "my QA/QC work is gone")
**Found in:** v3.47.0-alpha.2's "QA/QC redesign — fully custom time periods" batch — `loadProject()`'s `migrateQaqcWindows(...).then(...)` callback, `src/main.js`
**Description:** Loading a project saved before the custom-time-periods redesign correctly triggers `migrateQaqcWindows()` to convert its old fixed-peak-window recount data (keyed by label, e.g. `"1__Wednesday, April 22, 2026__AM peak"`) into the new custom-window shape — but that migration is fire-and-forget async (documented in its own comment as "windows just aren't visible for a few ms until it resolves"). If the user reaches the QA/QC or Analysis screen before the promise settles — which live testing showed takes anywhere from under 100ms to 2+ seconds depending on project size, not a fixed "few ms" — `renderQaqcScreen()`/`rerenderTripgenAnalysis()` already ran against the still-empty `tripgenQaqcWindows` and rendered "No time periods added yet" for every location. Nothing re-ran either function once the migration actually finished, so the screen stayed on that empty state **permanently**, not just briefly — reloading and re-navigating was the only way to get lucky enough to render after the migration had already resolved (why it appeared "flaky" during investigation: some navigation attempts happened to be slow enough to lose the race, others didn't). The underlying recount data was never lost (it round-trips through save/load fine, confirmed on the user's own file — 6 real recounts, real per-quarter scores), it was just unreachable in the UI when the race was lost.
**Root cause:** `migrateQaqcWindows(...).then(...)` (main.js, in `loadProject()`'s tripgen branch) updates `tripgenQaqcWindows`/`tripgenQaqc` but never triggers a re-render of whatever screen is currently showing.
**Fix:** The `.then()` callback now checks `_currentScreen` and calls `renderQaqcScreen()` or `rerenderTripgenAnalysis()` if the user is already on that screen when the migration resolves. Also added a synchronous "Loading…" placeholder to both `renderQaqcScreen()` and `rerenderTripgenAnalysis()` (guarded to only fire on a genuinely empty/fresh render, not on their several in-place re-render call sites triggered by small user edits) so a slow render — migration-related or just a large real project's own peak-score computation — never shows a blank screen with zero feedback while it works.
**Verified live, against the user's real save file** (not a synthetic fixture): reproduced the exact failure — navigating to QA/QC immediately after load showed "No time periods added yet" for all 3 locations and stayed that way even after a 2-second wait, before this fix. After the fix: same immediate click still briefly shows the pre-migration state (expected, correct), but within ~1 second self-corrects to show the real recount data (PM Peak window, hour found, per-quarter score detail, real volumes) with no further action needed — ran this exact race-condition repro 3 times in a row post-fix, consistent every time. Confirmed the Analysis screen path the same way. No console errors.

## BUG-044
**Status:** Fixed (v3.46.0-alpha.3)
**Severity:** Critical (a viewer's own local project data could be silently overwritten with someone else's shared project data)
**Found in:** v3.46.0-alpha.1 (Item 5, shipped as part of the original shareable-link feature) — `main.js`'s `window.addEventListener('beforeunload', ...)`
**Description:** Every autosave write path in the file is guarded with `if (isViewerMode) return;` — a deliberate, documented, structural guarantee that a `?share=<id>` viewer tab never writes to `localStorage`. The `beforeunload` handler (added to flush an in-progress count on tab close, unrelated to Item 5) was the one write path that predates `isViewerMode` and was never updated to check it. `loadProject(proj, {viewerMode:true})` still populates the live global state so the read-only render functions have something to read, which means `serializeCurrentProject()` — called unconditionally from `beforeunload` — would happily serialize the *shared* project and write it into the viewer's own `traffic-app-autosave` slot the moment they closed the tab or navigated away, silently clobbering whatever local project they'd been working on.
**Root cause:** `isViewerMode` was introduced in v3.46.0-alpha.1 and threaded through every autosave call site that existed *at that time*, but `beforeunload` (an older, pre-existing handler) wasn't audited as part of that change.
**Found via:** this task's required live re-verification that `localStorage` stays untouched by viewing — an early pass only checked writes around in-page interactions (clicking a `<details>` toggle) and missed the load event itself; a proper before/after snapshot around `window.__loadProject(proj, {viewerMode:true})` plus a real navigation-away (to trigger `beforeunload`) reproduced it immediately: `traffic-app-autosave` appeared in `localStorage`, containing the shared test project's data.
**Fix:** Added the same `isViewerMode` guard used everywhere else: `if (!projectType || isViewerMode) return;`.
**Verified live:** loaded a shared project via the real `?share=<id>` boot path (`isViewerMode` set by the real code, not simulated), then navigated away to trigger `beforeunload`; confirmed `traffic-app-autosave` was never created in `localStorage` afterward (previously it was, containing the viewed project's data). Re-confirmed the fix doesn't affect normal (non-viewer) sessions — `beforeunload` still fires and still writes for a real owner session, unrelated to this guard. `npm run build` passes.

## BUG-045
**Status:** Fixed (v3.46.0-alpha.4)
**Severity:** Critical (the "Enable sharing" button failed outright, with an alert, for any intersection or area-study project — likely the most common project types)
**Found in:** v3.46.0-alpha.1 (Item 5) — `enableSharing()`/`pushSharedUpdate()` in `src/share.js`, calling Firestore's `setDoc()`
**Description:** Firestore documents don't support arrays-of-arrays ("nested arrays") as a value type. An intersection project's serialized `periods[].vData` is `{in: [[...]], out: [[...]]}` (array of per-interval arrays), `pedData` is `[[[...]]]` (crosswalk × interval × direction), and `tmcData` is `{leg: {dest: [[...]]}}` (interval × vehicle-class 2D array per leg/destination) — all three nest arrays directly. `setDoc()` rejects the whole write with "Function setDoc() called with invalid data. Nested arrays are not supported." Confirmed live: clicking "Enable sharing" on a real intersection project with vehicle/pedestrian data failed with this exact error, shown to the user as a misleading "Could not enable sharing. Check your connection and try again." An area study embeds full intersection snapshots (same shape) and failed identically. Parking (no nested arrays) worked. **`tmcData` was found during this fix, not during the task that originally found BUG-045** — that task's live-tested project happened to have no TMC data, so the bug report only named `vData`/`pedData`; a field-specific fix would have missed `tmcData` and shipped a second, narrower version of the same bug.
**Root cause:** `serializeCurrentProject()`'s intersection/area shape was designed for `localStorage`/JSON export, which has no such restriction.
**Fix:** Rather than hand-listing every field that happens to nest arrays (proven fragile by the `tmcData` miss above), `src/share.js` now walks the *entire* payload generically: `encodeFirestoreArrays()` recursively finds any array that directly contains another array and replaces it with a self-describing marker object (`{__fsArr:true, n:<length>, v:{0:..., 1:..., ...}}`), applied immediately before every `setDoc()`. `decodeFirestoreArrays()` is the exact inverse, applied immediately after every `getDoc()`. Neither touches `serializeCurrentProject()`/`loadProject()`'s own canonical shape — this only exists at the Firestore write/read boundary, so localStorage and `.tcproject` file export are completely unaffected.
**Verified live:** enabled sharing on a real intersection project with real vehicle, pedestrian, AND turning-movement data (`test-fixtures/4way-full-vehicle-ped-tmc.tcproject`) — succeeded with no error (previously failed on this exact project). Opened the resulting share link in a separate tab and confirmed real, correct numeric data rendered throughout — peak hour, volume-by-interval, volume-by-vehicle-class, and the turning-movements dataset tab all showed real values (e.g. day total 5,310, peak-15-min 1,286), not `[object Object]` or any other decode corruption. Re-confirmed `localStorage` byte-for-byte unchanged in the viewer tab after forcing `scheduleAutosave()`. No console errors.

## BUG-043

**Severity:** Major (the whole read-only sharing feature was unusable in Firefox — one of the two major desktop browsers — with no error, just an indefinite hang)

## BUG-042
**Status:** Fixed (v3.45.0-alpha.4, user-reported live: recount data entered for one Trip Gen location appeared in a second, uncounted location's QA/QC screen — "it looks like it copies into fountain ave, and when i delete them from fountain ave, it deletes them from flatlands ave")
**Severity:** Critical (data corruption — two different locations' saved data became genuinely shared/aliased, not just misdisplayed; deleting a recount under one location's name deleted the other's real data)
**Found in:** pre-existing, likely since Trip Gen's multi-location model was introduced — exposed by any project with more than one location added after a project load
**Description:** `tripgenEntries` (the Trip Gen locations list) assigns each new entry's `id` from a module-level counter, `tripgenNextId`, incremented at every creation site (`id: tripgenNextId++`). `loadProject()`'s Trip Gen restore branch replaced the in-memory `tripgenEntries` array with the loaded project's saved entries but never resynced `tripgenNextId` to continue past whatever ids were already in use — it stayed frozen at its module-init value of `1`. So the first new location added in any session that began with a project *load* (the normal case — open the app, resume a project) got assigned `id: 1`, colliding with entry index 0's own id (also `1`, from the same never-resynced counter when *that* entry was created). QA/QC recount data is keyed by `` `${entryId}__${sheetName}__${peakLabel}` ``, so once two locations shared an id, they also shared every QA/QC key — recounts entered for one location wrote into, read from, and could be deleted from the exact same storage the other location's screen displayed. This is not a display bug: `tripgenQaqc` genuinely has one shared entry per peak, not two independent ones.
**Root cause:** `loadProject()`'s Trip Gen branch (`main.js`, `tripgenEntries.length = 0; tripgenEntries.push(...(proj.entries || []))`) never resynced `tripgenNextId` afterward. The adjacent, structurally identical `tripgenDistribution` restore, three lines below in the same function, does this correctly (`tripgenDistNextId = tripgenDistribution.reduce((mx, ix) => Math.max(mx, ix.id + 1), 1)`) — the Trip Gen entries path was simply missing the equivalent line.
**Fix:** Added `tripgenNextId = tripgenEntries.reduce((mx, e) => Math.max(mx, e.id + 1), 1);` immediately after entries are restored, mirroring the existing `tripgenDistNextId` pattern exactly.
**Verified live:** Playwright, using the user's actual corrupted save file (two locations, both saved with `id: 1`) as the load fixture. Loaded it, then used the real "add a location → begin counting" UI flow to add a third location. Before the fix this would have assigned the new location `id: 1` again (a third collision); after the fix it was assigned `id: 2` — confirmed by inspecting the autosaved project in `localStorage` after the change, which showed all three entries (`Flatlands Ave` id 1, `Fountain Ave` id 1 — the pre-existing corruption baked into the fixture itself, unaffected by this fix — and the new "Test New Driveway" entry correctly at id 2, not colliding). `npm run build` passes.
**Note on already-corrupted saves:** this fix prevents *new* collisions going forward but cannot retroactively repair a project file that was already saved with two entries sharing an id — the ids themselves need a one-time manual bump in the affected save file (done directly for the user's live file, outside version control; see DEVLOG).

## BUG-037
**Status:** Fixed (v3.44.0-alpha.2, reported by the user as "the table is too wide, we should have a default size... with each input (key press) the table reloads to far right side")
**Severity:** Major (broke live counting usability — table wider than the viewport, page itself horizontally scrollable, and the "current" table row's `scrollIntoView` call on every keystroke jumped the whole page horizontally to the far right instead of scrolling within an internal scrollbox)
**Found in:** pre-existing — `.tables-wrap` (CSS grid) in `index.html`, all 3 instances (Trip Gen counter, intersection QA/QC recount counter, main intersection vehicle counter)
**Description / root cause:** `.tables-wrap{display:grid;...}` had its per-instance `grid-template-columns` set to bare `1fr` (or `1fr 1fr` for the two-pane vehicle counter) via inline style. A bare `1fr` track implies `minmax(auto, 1fr)` — the `auto` minimum means the track won't shrink below its content's own minimum size. Since the wide, many-column count table inside (`.tmc-table{min-width:max-content}`) never wants to shrink, the grid track — and everything nested inside it, including `.tbl-scroll` (meant to have its OWN internal `overflow:auto` scrollbar, sized to fit its container) — grew to the table's full intrinsic width instead of respecting the screen's actual width. Confirmed live: with 7 classifications, `.tbl-scroll` measured 1678px wide inside a 1041px container, and the page's own `scrollWidth` (1926px) exceeded the viewport (1280px) — the classic CSS grid "blowout" bug. Because the overflow was happening at the PAGE level rather than being contained inside `.tbl-scroll`'s own scrollbar, the per-keystroke `scrollIntoView({block:'nearest'})` call on the current row (which only constrains the vertical axis) ended up scrolling the whole document horizontally to bring the oversized row into view, landing at the far right edge on every keypress.
**Fix:** Changed all 3 `.tables-wrap` inline `grid-template-columns` values from `1fr`/`1fr 1fr` to `minmax(0,1fr)`/`minmax(0,1fr) minmax(0,1fr)` — the standard fix for grid blowout, forcing the track to actually respect its container's width and let `.tbl-scroll`'s own `overflow:auto` do its job instead of the whole page absorbing the overflow.
**Verified live:** repeated the exact repro (7-classification Trip Gen count, wide table) — `.tbl-scroll` now measures 1008px inside its 1056px container (correctly contained, with its own horizontal scrollbar), and `document.body.scrollWidth` (1280px) now exactly matches `window.innerWidth` (1280px) — the page itself no longer overflows. Recorded several keystrokes and confirmed `document.documentElement.scrollLeft`/`document.body.scrollLeft` stayed at 0 throughout — no more far-right scroll jump. No console errors.

## BUG-029
**Status:** Fixed (v3.38.0-alpha.1, caught while building the matching per-group conflict check for Trip Gen — pre-existing, not caused by this session's earlier work)
**Severity:** Minor (only the red per-input `key-conflict` highlight was affected; the overall "duplicate keys" banner still correctly detected a conflict somewhere, and the conflict itself — sharing a key within one group of 4 vehicle types — is rare in practice since it requires 9+ vehicle types)

## BUG-022

**Found in:** new (`renderIntersectionQaqcScreen()`, added for area-study QA/QC)
**Description:** `renderIntersectionQaqcScreen(snapshotCtx)` is `async` (it `await`s `ixDetectPeakStart()` per QA/QC window) and unconditionally writes its result to the shared `#intersection-qaqc-list` container at the end (`root.innerHTML = ...`) with no check that it's still the most recently requested render. ## BUG-020
**Status:** Fixed (v3.29.0-alpha.1, caught during live verification of the QA/QC area-study feature)
**Severity:** Critical
**Found in:** pre-existing (`showIntersectionAnalysis`/`serializeCurrentProject`), exposed while adding area-study QA/QC's write path
**Description:** `showIntersectionAnalysis(idx)` (and the new `showIntersectionQaqc(idx)`) reassign the shared `activeIntersectionIdx` global purely for sidebar-highlight bookkeeping when a user drills into a specific area-study intersection — neither one reloads that intersection's data into the live counter globals (`periods`/`vPairs`/`intersection` stay whatever was last loaded live, which can easily be a *different* intersection). `window.scheduleAutosave()`'s area branch (`serializeCurrentProject()`) unconditionally does `areaIntersections[activeIntersectionIdx].snapshot = serializeIntersectionSnapshot()` — re-deriving from the live globals regardless of whether they actually match `activeIntersectionIdx`. **Verified live:** the task's required adversarial-ordering sequence (QA/QC intersection A → recount → switch to B → confirm independent → switch back to A → confirm A's recount persisted) — reproduced the corruption before the fix (in combination with BUG-021), confirmed clean after both fixes.

## BUG-017
**Status:** Fixed (v3.27.0-alpha.2, caught in post-implementation audit before push)
**Severity:** Major
**Found in:** v3.27.0-alpha.1 (the analyze/charts consolidation), never released
**Description:** The workspace sidebar's "Analyze" screen (`ix-analysis-content`) rendered its section headers (Summary, Data Quality, Turning Movements, Interval Detail) but every section body was empty — no stat cards, no chart, no tables — whenever the Count screen's inline "Analysis" pane (`counter-analyze-pane`) for the same project had been visited earlier in the same session.
**Root cause:** `renderAnalyzePeriodContent()` looked up its section containers via global `document.getElementById('analyze-summary-root')` (and five sibling IDs: `analyze-qa-root`, `analyze-tmc-root`, `analyze-bike-root`, `analyze-interval-root`, `analyze-compare-root`, plus `btn-share-report`). Both `#counter-analyze-pane` and `#ix-analysis-content` build their own copy of this markup with the same ids, and both can exist in the DOM simultaneously (one hidden via `display:none` at the screen level, not removed). `getElementById` always returns the *first* matching element in document order — `#counter-analyze-pane` sits earlier in the DOM than `#ix-analysis-screen`, so once the inline pane had rendered once, every subsequent paint call for the outer Analyze screen silently wrote into the inline pane's hidden, stale copy instead of the visible one.
**Fix:** Changed every one of those lookups from `document.getElementById(...)` to `root.querySelector('#...')`, where `root` is the pane-specific container already passed into the function — scopes each lookup to the pane actually being rendered, regardless of how many copies of the markup exist elsewhere in the DOM.
**Lesson:** This is exactly the class of bug that live-testing can miss without an adversarial ordering — the implementing agent verified each of the four analyze contexts worked when tested individually, but visiting the live pane and then the workspace screen *in the same session* is what actually reproduces it. Any future reused-markup-with-fixed-ids pattern across multiple simultaneously-mounted containers should scope lookups to the container, not the document.
