# Test fixtures

Reference `.tcproject` files covering the app's project types and counting modes, for quick
manual loading (Setup screen's project-load flow, or the landing page's "load project" input)
or for a future session to sanity-check a feature or regression. Each is a standalone,
plausible, internally consistent project file — not real field data.

All were generated by `_generate.mjs` (run with `node test-fixtures/_generate.mjs` to
regenerate after editing) and match the save format read/written by `src/main.js`
(`serializeCurrentProject` / `loadProject`) as of v3.42.x. If that format changes, regenerate
rather than hand-editing the `.tcproject` files.

Each was loaded live in the running app (via `window.__loadProject`) and confirmed to render
without console errors before being committed.

## Intersection projects (`projectType: "intersection"`)

- **`4way-vehicle-only.tcproject`** — standard 4-way, vehicle-in/out only (ped and turning
  modes disabled), single period. Baseline "simplest real project" fixture.

- **`4way-full-vehicle-ped-tmc.tcproject`** — standard 4-way with all three modes populated:
  6 vehicle types spanning 2 keybinding groups, pedestrian crosswalks on all 4 legs, and
  turning-movement counts on all 4 approaches — across 2 periods (AM/PM peak) with
  non-uniform, period-to-period-varying data. Exercises the full counting feature surface at
  once.

- **`5way-diagNE-oneway-tmc-only.tcproject`** — 5-way intersection with `diagLeg:'NE'`
  (non-default), the `W` leg marked `oneWayIn`, TMC-only (vehicle/ped modes disabled), across
  2 periods. The `NE` approach's destination list is `[E, S, N]` — both `E` and `S` classify
  as Left turns off the diagonal leg, and their relative order (`E` before `S`) is the exact
  shape the destination-ordering bug affected (stable-sort by turn classification, not
  reshuffled within a classification bucket). Use this to confirm that fix holds. Verified
  live: NE approach renders 3 movements in order "Left (E)", "Left (S)", "Right (N)" with
  populated per-interval data.

- **`3way-ped-only.tcproject`** — T-intersection (`missingLeg:'S'`), pedestrian-only (vehicle
  and turning modes disabled), single midday period.

- **`4way-tmc-only-empty-tmcdata-populated-vdata.tcproject`** — 4-way project configured as
  TMC-only (`mode:'turning'`, `enabledModes.turning:true`, vehicle/ped disabled) but with an
  **intentionally empty** `tmcData: {}` while `vData` holds real, non-zero, non-uniform
  counts — the "wrong-mode" corruption signature encountered with real field files (data
  saved for the wrong count type). Confirms the Data Quality "wrong mode" flag (added in
  v3.43.0-alpha.1 — see `BUGS.md`/`DEVLOG.md`) correctly fires on this shape.

- **`4way-multi-vehicle-groups.tcproject`** — 4-way, 8 vehicle types across 2 keybinding
  groups: group 1 (indices 0–3) is general traffic, group 2 (indices 4–7) is freight-only
  classes, each with its own distinct `tmcKey`. Reference fixture for group-customization
  work (in progress elsewhere — see `BUGS.md`/`DEVLOG.md`).

## Parking project (`projectType: "parking"`)

- **`parking-occupancy-3zones.tcproject`** — standalone parking-occupancy count, a separate
  project type from intersection counts. 3 zones (Front Lot, Rear Lot, on-street spaces) with
  distinct capacities, 30-minute intervals over an 8-hour window, occupancy rising and
  falling non-uniformly across the day (realistic AM-rise / midday-peak / PM-taper curve,
  each zone capped at its own capacity). Verified live: occupancy percentages update
  correctly per zone as the active interval advances.

## Area-wide study (`projectType: "area"`)

- **`area-study-corridor-3intersections.tcproject`** — a corridor study bundling 3
  intersections under one project: two 4-way intersections and one T-intersection, each with
  its own street names, vehicle + pedestrian data (1 AM-peak period), and distinct counter
  names/coordinates. Exercises the area-study hub's multi-location structure
  (`intersections[]`, each carrying a full intersection-project `snapshot`). Verified live:
  all 3 intersections list correctly in the study hub with their period counts.

## Regenerating

`_generate.mjs` is deterministic (fixed PRNG seed per fixture) — re-running it reproduces
identical output. Edit the generator, not the `.tcproject` files directly, if the data shape
needs to change; hand-edited JSON is easy to get subtly wrong (e.g. destination arrays that
don't match `classifyTurn`'s stable-sort order, or `tmcData` column counts that don't match
`vPairs.filter(p => p.includeTmc).length`).
